# 路由设计（v1）

## 1. 目标

v1 的路由只有一个动作：**根据请求协议和模型名，查到一组候选上游**。

```
(protocol, model) ──查表──> []Target{instance, base_url, upstream_model}
```

第一个候选是主实例，其余是备实例。主实例失败时按顺序往后切换。

没有规则引擎、没有权重轮询、没有跨协议转换。

## 2. 两层模型

路由表由两层配置编译而成，二者的职责严格分离：

| 层 | 是什么 | 持有 |
|---|---|---|
| **Instance** | 物理上游接入点 | 地址、账号 Key、协议入口、**支持的上游模型名**、熔断参数 |
| **Model** | 逻辑模型 | 对外名、上游名、分流策略、候选实例链 |

这样划分的原因很实际：一个账号通常能提供多个模型，一个模型也常由多个账号提供 —— 这是**多对多**关系。把模型挂在账号下面（早期版本的做法）会导致「两个账号提供同一个模型」无法表达，把策略挂在账号下面则无法让不同模型用不同策略。

- **实例**不携带任何分流策略：同一个实例可以被任意多个模型引用，各模型自带策略与优先级。
- **模型名全局唯一**：同一个对外模型名只能定义一次，因此路由键 `(protocol, model)` 永远唯一。
- **能力与选择分离**：实例声明「能服务哪些上游模型名」（必填），模型声明「要用哪些实例」。加载和保存时校验每个候选实例都声明了该模型的上游名，把「挂错上游」挡在配置阶段。

## 3. 索引构建

启动或配置重载时，先把实例展开成路由就绪形态（内置端点在这里补齐协议入口），再遍历模型：

```go
for _, m := range models {
    for _, cand := range m.Instances {   // 已按 priority 升序
        inst := instances[cand.Instance]
        for _, ep := range inst.Endpoints {
            k := key{ep.Protocol, m.Name}
            idx[k] = append(idx[k], Target{
                Instance: inst.Name,
                BaseURL:  ep.BaseURL,
                Key:      inst.APIKey,
                UpstreamModel: m.Upstream,
            })
        }
    }
}
```

**硬约束**：模型名全局唯一；模型的 `upstream` 必须出现在每个候选实例的 `models` 声明里。任一不满足都拒绝加载，报出具体位置。这样路由结果永远可预测。

候选链的顺序由 `priority` 决定（数字越小越优先），同优先级按配置顺序。

## 4. 查询

```go
func (r *Router) Resolve(protocol, model string) ([]Target, error) {
    if t, ok := (*r.snapshot.Load())[key{protocol, model}]; ok {
        return t, nil
    }
    return nil, &ModelNotFound{Model: model, Protocol: protocol}
}
```

`ModelNotFound` 会提示该模型是否存在于另一个协议，帮助用户改 base_url：

```
model "glm-4.6" is not configured for the OpenAI protocol;
it is available via the Anthropic endpoint (/anthropic)
```

## 5. 失败切换

候选链上的实例按顺序尝试。判定规则：

| 上游结果 | 是否切换 |
|---|---|
| 连接失败 / 超时 | 切换 |
| `5xx` | 切换 |
| `429` | 切换 |
| `4xx`（400 / 401 / 404 …） | **不切换**，原样透传给客户端 |
| 客户端断开 | 不切换 |

`4xx` 描述的是请求本身，换一个上游重试只会重复失败；`429` 与 `5xx` 描述的是上游，换一个实例可能成功。

**流式响应的边界**：切换只发生在拿到上游响应头之前。响应头一旦返回，网关已经把状态行写给了客户端，此时再换上游会让客户端收到两份 SSE 流，因此流中途断开只能报错，不重放。

每次尝试各记一条请求日志，失败的条目带上失败的实例名，因此事后能看出「为什么切了」。

## 6. 熔断

一个持续故障的实例不应该让每个请求都先付一次超时。实例级熔断参数：

- `max_fails`：连续失败多少次后跳过一次（默认 3）
- `cooldown_secs`：跳过多长时间（默认 30 秒）

熔断状态放在网关进程内，**不进路由快照** —— 否则每次改配置热重载都会把计数清零，刚被摘除的实例立刻复活，比没有熔断更糟。冷却结束后实例会被重新探测。

熔断是**物理层**的属性：某个实例连不上，对引用它的所有模型都是故障，所以参数挂在实例上而不是模型上。

## 7. 协议隔离

协议来自 URL 前缀，在 ingress 阶段确定，路由层不接收 `headers`，从结构上杜绝跨协议命中。候选链按协议分别构建，一个只提供 OpenAI 入口的实例不会出现在 Anthropic 端点上。

## 8. 按时段调度候选（峰谷计费）

部分厂商在特定时段打折（DeepSeek 的错峰价是典型例子）。为了让网关在谷时自动切到便宜的厂商，
候选接入点可以挂**时间窗口**：

```yaml
schedule:
  timezone: "Asia/Shanghai"

models:
  - name: deepseek-chat
    upstream: deepseek-chat
    instances:
      - name: deepseek
        priority: 10
        windows:
          - start: "00:00"
            end: "08:00"
            priority: 0
      - name: glm
        priority: 1
      # only: true：这个候选只在窗口内参与路由，窗口外直接跳过
      - name: limited-quota
        priority: 2
        windows:
          - start: "00:00"
            end: "08:00"
            only: true
```

### 8.1 判定规则

给定当前时刻 `t`（已换算到 `schedule.timezone`）：

| 步骤 | 规则 |
|---|---|
| 命中 | 窗口是左闭右开 `[start, end)`；`start > end` 视为跨天，此时 `t >= start \|\| t < end` |
| 生效优先级 | 命中窗口里所有 `priority` 的最小值；没有命中窗口带 `priority` 时取基础 `priority` |
| 可用性 | 候选若带 `only: true` 的窗口，则**仅**在命中某个 `only` 窗口时可用；否则恒可用 |
| 排序 | 按生效优先级升序稳定排序；相同则「命中了窗口的候选」在前，再相同则按基础优先级 |

`only: true` 与 `priority` 可以同时出现在一个窗口里：窗口内按窗口优先级排序，窗口外该候选不参与路由。

### 8.2 时区

`schedule.timezone` 是**全局唯一**的时区来源，所有窗口共用它：

- 默认 `Asia/Shanghai`；
- 支持 `"UTC"`、IANA 名称（如 `America/New_York`）、固定偏移（如 `+08:00`）；
- 时区名写错在加载配置时就报错，不会等到运行时才发现窗口整体偏移；
- 二进制内嵌了时区库，不依赖宿主机是否装了 tzdata。

选全局时区而不是每个窗口各自带时区，是因为一个部署只服务一个团队，峰谷时段也只有一个口径；
窗口里再写一遍时区只会带来不一致的风险。

### 8.3 生效时机

窗口判定发生在**每次请求解析候选链时**，不是靠定时器切换：

- 跨过时段边界后，下一个请求自动用新的顺序，不需要重启、不需要重载配置；
- 快照里保存的是编译后的窗口（起止分钟 + 覆盖优先级），运行时只做一次时间比较和一次小规模排序；
- 时区在加载配置时就解析成 `*time.Location` 并放进快照，运行时不做时区查表。

配置里的**基础优先级顺序**仍然保留：它既是窗口外的顺序，也是生效优先级相同时的兜底顺序。

### 8.4 边界情况

- 某个候选的窗口当前全部关闭 → 该候选被踢出候选链；若所有候选都被踢掉，请求返回 `503`
  （区别于「模型没配好」的 `404`）；
- 窗口只影响**候选链顺序**，不改变协议隔离：窗口不会把只提供 OpenAI 端点的实例塞进 Anthropic 入口；
- 一个请求在开始时确定候选链，之后即使跨过时段边界也不会中途换上游；
- 熔断与窗口正交：熔断管实例是否可用，窗口管实例排第几。

## 9. 演进路径

`router` 包对外只暴露 `Resolve(protocol, model) []Target`。将来引入规则时：

1. 在查表之前插入规则匹配；
2. 候选从 `[]Target` 变为更丰富的候选描述；
3. 选择策略（权重 / 优先级 / 熔断）在 router 内部实现。

ingress、transport、日志、管理台均无需改动。

`strategy` 字段已经预留（当前只实现 `failover`）。将来加轮询或按权重分配时再引入对应的字段，不需要改路由键与候选链的结构。

时间窗口已经是这条路径上的第一步：候选从「一个静态 Target」变成「带上下文的 Target」，
选择规则留在 router 内部，ingress 与 transport 仍然只认顺序。

## 10. 测试

- 表驱动：`(protocol, model)` → 期望候选链 / 未命中。
- 冲突检测：模型名重复 → 加载失败，错误包含重复的名字。
- 跨协议提示：模型只在另一协议存在时，错误信息给出提示。
- 候选链排序：按 `priority` 升序，同优先级按配置顺序。
- 时间窗口：窗口内插队、窗口外回落、跨天窗口、`only` 排除、全部候选关闭时报 `503`。
- 失败切换：5xx / 429 切换、4xx 不切换、全部失败返回最后一个上游错误。
- 熔断：达到阈值后跳过实例，冷却结束后恢复。
- 热更新：替换快照后进行中的请求仍使用旧 Target。
